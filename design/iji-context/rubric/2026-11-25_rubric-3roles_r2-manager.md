## 観点ごとの点と理由

### 導入の判断材料　19 / 25
良い点
- 「できないこと」が独立した節で、入院・DPC は点検しない、審査の医学的な判断はしない、算定を一から計算しない、効果は測っていない、まで書いている（README.md:43-51）。言い過ぎを避けている。
- 「必要なもの」（README.md:53-58）と「導入したら最初にすること」（README.md:86-91）があり、デモ／実在の選択が後から変えられないこと、公開マスターがないと G01〜G12 が「見ていません」になることが分かる。
- 背景の数字はすべて出典つきで、EM の採用値（1-1・4-1・4-2・9-1）と一致した。

引いた点
- 費用の目安がない。「利用料はキーを持つ人にかかります」（README.md:57）だけで、1 か月・1 クリニックでどのくらいかかるかの目安や測り方がない。経営判断に一番要る材料。
- 公開版（README.md:78）を誰が運営し、サーバーの管理者が誰か（security.md:20 の「サーバーの管理者は DB とファイルを直接読める」の「管理者」）が書かれていない。実在のデータを入れてよいと書く以上、相手が分からないと入れる判断ができない。
- 職員のパスワードの再発行・変更の手段がなく、持ち主の引き継ぎもない（後述）。その旨も README にない。
- README の組み立てが崩れている：「職員の管理」が「データと安全」の後ろ、security.md への案内の下にはみ出している（README.md:104）。README.md:90 は「→ docs/masters.md」の直後に改行なしで万病辞書の話が続く。

### データと同意　20 / 25
良い点
- 注意書き（config/notice.json）が、外部の事業者名・日本の外であること・氏名を外せない入力・暗号化していないこと・送った内容は消せないことを明記。画面の同意（app/consent.tsx）と `POST /api/consent` で版ごとに記録され、監査ログにも残ることを確かめた。
- 送るもの・送らないものの表（security.md:27-42）、外国にある第三者への提供は「確かめていない」と正直に書く（README.md:96）。
- クリニックを消す画面（app/settings/erase-clinic.tsx）は、消すもの・消せないものを並べ、チェックと持ち主の ID の入力の 2 段。API でも確かめの ID 違いは 400、実行後はログインできないことを確かめた。

引いた点
- docs/security.md に「クリニックを消す」が書かれていない。「消す操作は 3 つあります」（security.md:55）のままで、クリニックをまるごと消す操作、そのとき監査ログも消えること、ログインの記録（auth_events）は残ることが載っていない。マージのコミット（7ddb644）は「security.md にクリニックの削除を書く」としているが、実際に足されたのは職員の行だけ。README.md:102 は「全体は security.md」と案内しているので、案内先が欠けている。
- README の「消し方」（README.md:100）に、査定・返戻の CSV を消せることがない（security.md:55 と注意書きにはある）。同じ段落で「AI のサービスに送った内容は消せません」が 2 回続く。
- クリニックを消すと監査ログも一緒に消え、消す前に書き出す手段がない。院内の記録の保存の決まりがある医療機関では、消す判断がしにくい。

### 管理のしやすさ　13 / 20
良い点
- 設定の画面に、役割・職員（停止・再開・役割の変更）・招待（発行・一覧・取り消し）・施設の申告・公開マスターの状態・クリニックを消す、がそろう（app/settings/page.tsx）。
- 事務長がいなくなる操作はサーバーが断る（自分を事務長から外す操作が 409 になった）。停止するとその人のセッションも切れた。操作はすべて監査ログに残った。
- 施設の申告は、確かめた人の名前と日・確かめ直す日を持ち、事務長レポートの画面に「確かめ直し」の知らせが出る（app/manager/recheck.tsx）。

引いた点
- レセメン会議を事務長が回せない。議題は見られるが、「今すぐ整理を回す」も議題への回答もベテランだけ（src/server/policy.ts:213-215）。`POST /api/meeting` は事務長で 403「この操作は『ベテラン』の役割で行います」になった。しかも会議の画面は役割を見ずにボタンを出す（app/meeting/page.tsx:139・166）ので、事務長は押してから断られる。2 人以上のクリニックでは事務長は役割を切り替えられない（auth.ts の switchRole）ので、ベテランがいないクリニックでは会議が止まる。知識の承認（検証）もベテランだけ。
- 持ち主を引き継げない。持ち主は停止できず（src/server/auth.ts:272）、持ち主を別の人に移す操作もない。持ち主が辞めてもアカウントが残り、クリニックを消せるのはその人だけ。
- パスワードを忘れた職員を戻す手段がない（再発行・変更の API も画面もない）。停止して別の ID で招き直すしかなく、その人の記録が別人になる。
- 事務長レポートに期間がない。集計は提出済みの全部の問題を数えていて月で分けていない（src/server/app/prevented.ts:18）のに、画面の頭のコメントと spec は「月次」と言う（app/manager/page.tsx:2）。画面の文（app/manager/page.tsx:37）にも期間がない。

### 効果の示し方　12 / 15
良い点
- 「効果は測っていません」と README で言い切り（README.md:50）、事務長レポートの画面も「レセメンの効果の大きさとしては読めません」「金額は推定」と書く（app/manager/page.tsx:37）。
- 測り方として、査定・返戻の突き合わせの手順（docs/review-test.md）と院長の同意の雛形（docs/review-consent.md）があり、割合を出さない・件数だけ持ち出す、まで決めている。見逃しは突き合わせの記録がなければ数えない（0 件と言わない）。

引いた点
- 期間のない累計の円を大きく出しているので、経営会議に持ち出すと「今月これだけ効いた」と読まれやすい（上の期間の件）。
- API は「記載もれ」の件数を返すのに、画面の型が落としていて出ない（app/manager/page.tsx:10-16。src/prevented/prevented.ts の summarize は返している）。
- 事務長レポートの初期状態は全部 0 件 0 円。デモで登録した直後に、事務長が数字の出方を見る手順が README にもデモの台本にもない。

### 医師との関係　12 / 15
良い点
- 医師確認は 7 要件・点数金額に触れない・「その他」「判定不能」を必ず入れる、が README・画面（app/doctor/page.tsx:35）でそろう。翌営業日のリマインドと 3 営業日で保留（src/query/doctor-query.ts）。
- 略語の問いを同じ月・同じ略語で患者をまたいで 1 問にまとめ、医師の答えを辞書に書き足す（README.md:27）。医師の負担を減らす工夫がある。
- 実在のデータのクリニックでは、医師の役割は医師の招待で入った人だけ（持ち主が医師を名乗れない）。

引いた点
- 医師確認の画面のお願いの文が「わかりやすいカルテが、クリニックの健全な経営への第一歩です」（config/doctor-abbrev.json:3）。問いの外の欄とはいえ、医師に経営の話を持ち込んでいる。点数・金額に触れない方針の趣旨からは外したい。
- 「医師確認の答えで直した」の件数と円が事務長に出る。画面は「医師に金額を示す材料や、医師を評価する材料ではありません」と書くが、spec FR-55（spec.md:156）とコードの注記（src/prevented/prevented.ts:7）は「医師側の取りこぼしを示す材料にする」「事務長から医師へ伝える材料」と書いていて、狙いが食い違う。どちらが正か分からない。
- 事務が Lv.4 までのあいだは、辞書で意味を選んでも医師確認に回る（README.md:27）。新人の多いクリニックでは医師の問いが増える。件数の見込みがない。

## 100 点に届くための直しの順
1. 会議と知識の承認を事務長にも開くか、事務長の画面でベテランを決める道を示す。少なくとも会議の画面で、回せない役割にはボタンを出さず「ベテランが回します」と書く（#1）
2. 事務長レポートに診療月（または提出月）の期間を付け、月ごとに切り替えられるようにする。記載もれの件数も出す（#2・#9）
3. 持ち主の引き継ぎと、事務長によるパスワードの再設定（または再設定用の招待）を足す（#3・#4）
4. docs/security.md の「消せるもの」にクリニックを消す操作と、消えるもの（監査ログを含む）・残るもの（auth_events・外部に送った内容）を足し、README の「消し方」に CSV を足す。README の「職員の管理」を「機能の一覧」か「必要なもの」に移す（#5・#6・#7）
5. 消す前に監査ログを書き出せるようにする（#8）
6. 費用の目安（1 か月・1 クリニックの API 利用の実績か測り方）と、公開版の運営者・サーバーの管理者を README に書く（#12）
7. 医師へのお願いの文から経営の話を外し、FR-55 の狙いを画面に合わせて決め直す（#10・#11）
8. Lv.4 までの医師確認の件数の見込みか上限を示す（#13）

## 確信度と見られなかったもの
- 確信度：中〜高。API とコードで確かめた点は高い。画面の見た目はブラウザを使えないので、文言はコードで読んだ。
- 見られなかったもの
  - 画面の実際の描画（ボタンの位置・折りたたみ・スマホの幅）
  - 事務長レポートに数字が入った状態（デモで登録した直後は全部 0 件で、問題を提出して確定する流れまでは回していない）
  - 会議の議題が出る状態（時計を進める操作は試していない）と、ベテランの役割での回答
  - 持ち主でない人がクリニックを消そうとしたときの API の応答（2 人目は停止のときにセッションが切れ、再ログインはしなかった。コードの assertCanEraseTenant で 403 を確かめた）
  - 公開版（sslip.io）・実在のデータのクリニック
- 自分のクリニック（r2-manager と、招いた r2-manager-staff）は、採点の最後に「クリニックを消す」で消した。ほかの人のデータには触っていない。

### 指摘

- [C-94] 種別: 設計 / 深刻度: high
  - 指摘: 実在の UKE を受け取るのに、請求 id を RE の「カルテ番号等」（13 列目。uke.ts:116・224）から取り、「取り込み済みと同じ請求 id は断る」（§11-6・§11-11「形式の検査は今のまま」、server/app/uke.ts:99-101）を残している。カルテ番号は患者ごとの番号で、請求ごとの番号ではない。しかも記録は任意の欄である。合成データでは一意になるよう作っていたので表に出なかった。
  - 破綻シナリオ:
    1. 2026年10月分の UKE を取り込んだあと、同じ診療所の 11 月分を上げると、継続して通っている患者は全員 10 月と同じカルテ番号を持つ。このため「すでに取り込んだ UKE と同じ請求 id で、内容が違う」でファイルごと断られる。在宅の患者は毎月同じ人なので、2 か月目以降の実データはほぼ必ず受け取れない
    2. §11-12 の目的「昔のカルテを今の算定に入れたら」で、2025年3月分を取り込んだ後に今月分を上げても、同じ理由で断られる（その逆の順でも同じ）
    3. 1 つのファイルの中に、同じ患者のレセプトが 2 枚ある（月の途中で保険が変わった、公費の単独のレセプトが別にある）と、「同じ請求 id のレセプトが 2 つある」でファイルごと断られる。カルテ番号を空にしている医療機関のファイルは、`UKE_CLAIM_ID`（1 文字以上。limits.ts:16）で全件が断られる
    4. 断る検査を外して受け取る形にすると、こんどは §11-11 の削除（請求 id にぶら下がる提出・適用記録・医師確認などを消す）が、別のファイルの同じ患者の記録まで消す。完了条件の「別のファイルの同じ患者は残る」と食い違う。`caseOf`・`/api/uke/claims/[claimId]/trial` も、どちらの月か決められない。`fixtureOf`（cases.ts:72）は請求 id で同梱の症例を引くので、カルテ番号が K1〜K7 の請求 id と同じ実在のレセプトには、合成の事実と出来事が付いてしまう（今は upload の時点で断っているが、それは 3 と同じ「ファイルごと断る」になる）
  - 提案: 実在の UKE の請求 id は、取り込みの側で振る（例：`<ファイルの sha256 の先頭>-<RE のレセプト番号>`。同じファイルの中で一意で、ファイルを消すときの単位とも一致する）。カルテ番号は患者マスタに寄せる手がかりの 1 つにとどめ、空でも受け取る。「取り込み済みと同じ請求 id」の検査は「同じ内容のファイル（sha256）」の検査に替える。同梱の見本は今の id のままにする。完了条件に「同じカルテ番号の患者を含む 10 月分と 11 月分を続けて取り込める」「同じ患者の 2 枚のレセプトを含むファイルを受け取れる」「カルテ番号が空のファイルを受け取れる」「片方のファイルを消しても、もう片方の記録が残る」を足す。

- [C-95] 種別: 設計 / 深刻度: mid
  - 指摘: 点数の食い違いで「断る」処理が `mapClaim` に入った。`cases()` は保存した UKE を開くたびに読み直す（cases.ts:84）ので、`mapClaim` が例外を投げると、C-90 と同じく一覧がまるごと止まる。§11-12 で版がないことによる止まり方は閉じたが、別の引き金で同じ形が残る。
  - 破綻シナリオ: `codes` は追記専用の表で、実データを受けるほど行が増えていく。取り込んだ時点では、引けないコード（ある加算）を含んでいたため対象外だった単位がある。後の更新でそのコードを `accept` に足すと、その単位が区分に引かれるようになる。そのときに区分の点数の合計が UKE の 1 回分の点数と合わなければ（減算のある項目、点数表の値の修正など）、`mapClaim` は「行番号つきで断る」。これは取り込みのときではなく、`cases()` のたびに起きる。`caseOf`・通知の対応づけ・知識の一覧が 500 になり、同梱の K1〜K7 も開けなくなる。
  - 提案: 「断る」は取り込みの入口でだけ行うと書く。保存済みの請求を `mapClaim` で読み直したときに食い違った単位は、例外にせず対象外（`others`。理由つき）に落とす。完了条件に「取り込み済みの UKE のコードを `codes` に足しても、一覧が動く」を足す。

- [C-96] 種別: 設計 / 深刻度: mid
  - 指摘: `commentOn` を「その区分の行と同じ単位に、コメントがあるか」で見るとしているが、エンジンの行は単位の番号を持たない。`mergeLines` が同じ区分の行を束ねるうえ、`deriveLines` のコメント（`{ rule; code; text; status }`）にも `unit` がない。このため設計どおりには計算できない。今の match.ts:37-39 は `x.kubun` で見ていて、型の変更で壊れる。
  - 破綻シナリオ: 実装者は、行に `units` を足すか、コメントに区分を推測で付けるかを、その場で選ぶことになる。前者は `ClaimContext.lines` の型の変更なので、エンジン・導出・選択モードに波及する。後者は、1 つの単位に複数の区分がある場合（往診料＋緊急往診加算の単位の理由の CO）に、片方の区分の知識だけが当たらない。カルテ由来の請求（算定プレビュー）では、どちらにしても単位がないので、`commentOn` の知識はいつも `present: false` として当たる。
  - 提案: `mapClaim` で、コメントに「置かれていた単位に入っている区分の集合」（`kubun: string[]`）を付け、`commentOn` はそれで見ると書く。導出のコメントは、`CommentRule.kubun` から付ける。行の型は変えない。

- [C-97] 種別: 設計 / 深刻度: mid
  - 指摘: `outbound` が「呼び出し元のルートの申告（`external`）を引数で受け」る形では、ハンドラやその下の関数が文字の `"ai"` を渡せば通ってしまう。この確認は申告漏れを機械で止めることにならない。完了条件 (b) も import の場所しか見ていない。
  - 破綻シナリオ: `external: "none"`・`patientData: false` と申告したルート（同意が要らない）から呼ばれる共通の関数が、後の変更で事実の読み取りを呼ぶようになり、`outbound.extract(text, "ai")` と書く。型もテストも通り、同意していない利用者の入力が Anthropic に送られる。
  - 提案: `route` が、`external ≠ "none"` のときだけ、偽造できない値（`route` の中でだけ作れる型の値、または AsyncLocalStorage に置いたルートの申告）を渡す。`outbound` はそれを要求し、ないか `"none"` なら例外にする。完了条件に「`external: "none"` のルートから `outbound` を呼ぶと例外になる」を足す。後から変えると全部の呼び出し元を直すことになるので、実装の前に決める。

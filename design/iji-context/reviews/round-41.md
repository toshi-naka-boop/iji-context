### 指摘

- [C-180] 種別: 設計 / 深刻度: mid
  - 指摘: 押した事実を `@rev` で知識に結んでも、「要再検証から戻した知識では前の押下は効かない」（14-3・14-5 の完了条件）は成り立たない。今の rev は内容のハッシュで、状態の移り変わりでは変わらないため。
  - 破綻シナリオ: `KnowledgeMeta.rev` は「SKILL.md 本文・match・polarity・matchApprox・conditionNote の内容ハッシュ」（src/lifecycle/types.ts、store.ts の computeRev）。状態を変えても計算し直されない。たとえば、知識 K（allow）を承認済みにした状態で、10 月の請求 A と 11 月の請求 B に Lv.6 の事務が「この請求も条件に当たる」を押す。A が返戻され、localReturn で K は要再検証になり、A の押した事実は取り消される。会議でベテランが文を直さずに K を承認し直すと、K の rev は前と同じになる。そのため、B に残った `local:K@<同じ rev>:…` がそのまま効き、B の組は誰も押し直さないまま出ない。14-5 の完了条件「要再検証から戻ると、前の押下は効かない」は、rev を比べる実装では満たせない。テストを rev の変化だけで書けば通ってしまい、要再検証から戻す道は試されない。
  - 提案: 押した事実が効く条件を「知識が今も承認済み、rev が同じ、押した時刻（checked_at）が知識の status_since より後」にする（status_since は「今の状態に入った日」で、承認し直すと進む）。あるいは、承認に入るたびに進む世代の番号を key に入れる。完了条件にも「直さずに承認し直した場合」を書き足す。

- [C-181] 種別: 設計 / 深刻度: mid
  - 指摘: 改定の棚卸で「改定前後のどちらかの 1 枚がない → 要再検証（安全側）」としているが、これは利用者の判断「差分が出たものだけ」とぶつかる。しかも安全のためには要らない。
  - 破綻シナリオ: config/calendar.json の改定日は偶数年の 06-01。マスターはリポジトリに入れず、利用者が手で取り込む（CLAUDE.md）。2028-06-01 を過ぎたあとの最初の週の会議で、利用者が令和10年度の基本マスター・電子点数表をまだ入れていないとする。この場合、「改定後の 1 枚がない」ので、codePair を持つ承認済みの知識が全部要再検証になる。これは利用者が「言い間違い」として退けた「全部」の棚卸と同じ結果である。さらに、要再検証の知識は会議で通さないまま 180 日たつと IDLE_EXPIRED で消える（triggers.ts）。一方、改定後の版がない診療年月の請求は、そもそも判定しない（CLAUDE.md の固定条件）。改定前の月の請求には、改定前の 1 枚がそのまま正しい。つまり、1 枚がない間に知識が誤って使われる請求はない。今の evaluateOne は「改定日が status_since より後」のあいだは会議のたびに判定し直すので、何も出さずに次の会議へ回しても漏れは起きない。もう一点、比べるものの 3 つ目「EM §2-12 の HP・例外」は世代ごとに持っていない（EM の 1 枚の表で、引用は令和8年度の告示）。「改定前と改定後で差が出たか」は、この部分では決まらない。
  - 提案: 1 枚がない・表がないときは、イベントを出さずに保留する（会議の議題に「改定後のマスターが未取り込み」と出す）。EM の部分は、改定前後の比較ではなく「その組に HP が入った・変わったら」と別の条件で書く。または、比べるものから外して 14-3 の最後の行（EM の決まりがあれば使わない）に任せる。

- [C-182] 種別: 設計 / 深刻度: mid
  - 指摘: 返戻の入口を「押した事実 local:* がある組」に限ると、Lv.1〜4 がヒントの条件を見て算定し、返戻された場合に棚卸が起きない。承認済みの allow が残り、Lv.5 以上は押し続ける。
  - 破綻シナリオ: 組 X に承認済みの allow がある。Lv.3 の事務の 10 月の請求には、14-3 の表どおり「確かめてください」とヒント「院内の知識：条件に当たれば併せて算定できます。条件：〜」が出る。ボタンはない。事務はヒントの条件に当たると読んで、両方を算定して提出する。12 月に組 X で返戻される。この請求には local:* の事実がないので、「この請求のこの組が返戻・査定された」は出ず、localReturn は起きない。K は承認済みのままで、Lv.5 以上は 12 月以降も押して指摘を消す。残る手は、事務が avoid を作り、ベテランが承認して「食い違い」にすることだけ。承認されるまでは allow が効き続ける。利用者の判断「返戻ではその返戻に関わった組の知識」の「関わった」は、ヒントとして添えて使われた知識も含むと読むのが自然である。14-3 ではヒントとして添えたときも USED を出しているので、使われた記録はすでにある。
  - 提案: 返戻の入口を出す条件を「その請求のその組に、承認済みの codePair の知識を添えた（押した事実がある、またはヒント・local_avoid として添えた）」に広げる。サーバーでは G05 を計算し直して照らす。完了条件に「Lv.4 の請求で、ヒントを添えた組の返戻」を足す。

- [C-183] 種別: 前提 / 深刻度: mid
  - 指摘: Lv.1〜4 に院内層の知識の条件をヒントとして見せることは、spec.md の FR-12「院内ローカルルールは新人への助言に使わない（決定8）」と食い違う。§14 はこれに触れていない。

  - 提案: 利用者に確かめる。FR-12 の範囲は「メンター（Skill・AI の助言）」に限り、ルールエンジンの指摘に添える院内の知識は別とするか。そう決めたら、spec.md の FR-12 に但し書きを足し、§14-3 にも「FR-12 はメンターの助言の規定で、ここには掛からない」と書く。

- [C-184] 種別: 前提 / 深刻度: low
  - 指摘: F10 のレベル（処理件数の累計）を、指摘を消せる権限の線引きに使っている。しかしレベルは、正誤を問わない完了の件数で数える。ベテランの役割を持つ人が Lv.1 のこともある。権限の基準としての前提が確かめられていない。
  - 破綻シナリオ: score（src/practice/practice.ts）は、完了した問題を正誤に関係なく 1 件（選択モードは 0.5 件）と数える。startDrill は同じ練習問題を何度でも始められる。そのため、Lv.1 の事務でも、同じ練習問題を 180 回終えれば Lv.5 になり、「この請求も条件に当たる」で G05 を消せる。逆に、院のベテラン（role=veteran）が取り込んだレセプトの点検（/uke/[claimId]。問題を作らないので件数に入らない）だけを使っている場合は Lv.1 のまま。知識を承認した本人が、ボタンを押せない。また FR-16 は「他人のレベルは見せない」だが、押した事実は確かめた人の名前つきで請求の事実に出る（claimFacts の checkedByName）。そのため、同じ請求を見た同僚から「この人は Lv.5 以上」と分かる。

## 1. 目的

メインテーマ: **『働くが楽しくなるAI』— 医療事務編**

作者は医療機関の採用を仕事にしている（紹介手数料を払う側）。医師・看護師には紹介料を払って採り、辞められ、また払う。一方で医療事務は、辞めたら困るのに紹介料を払ってまでは採らない職種（厚労省の手数料公表対象職種に入っていない。病院の紹介会社利用率は事務職員15.4%（2020年）、医師73.1%・看護師83.5%（2026年）: EM #3-2, #5-5）。なぜ辞めるのかをヒアリングで掘ると、給与や業務量の奥に『楽しくない』という言葉が出てきた（2026-11-02 ヒアリング）。その裏には、頼られない・声が届かない・終わりがない、という楽しくなさがあり、そこに日本特有の構造がある：

- 無資格で就ける事務とされ「誰がやっても同じ」と見られる。唯一の公的寄りの試験（診療報酬請求事務能力認定試験）は2025年12月で終了、実施団体は2026年3月に解散（EM #18-3）
- カルテが足りなくても医師に言えないヒエラルキー。「医師に記載を確認する」手続きに日本では制度名すらない（EM #13-2）。米国では Physician Query として標準化されている（EM #19）
- 返戻のたびにルールが積み上がり、誰も捨てられない。都道府県別の審査基準は支払基金約33,000件・国保連約18,000件（EM #9-1）
- 医療事務固有の離職統計は国にも業界団体にも存在しない（EM #2-1）。測られてすらいない

レセメンは、レセプト請求を担う医療事務一人ひとりにAIメンターをつける。カルテから算定までを一緒に進め（診察直後の算定伴走、月末の事後点検バッチではない: EM §6-5）、医師への確認はメンターが引き受け、わからないことはメンター同士が解く。経営の根幹を支えているのに声が届かなかった医療事務が、頼られ、楽しく働けるようになるためのAI。

入口は「働くを少しでも楽しく」、出口は「医療事務＝クリニックの収支を支える経営部門」。今回は医療事務から始めるが、同じ仕組みは看護師・医師にも広げられる。

訴求に使う数字は公式3指標（査定率0.40%／返戻率0.460%／復活率35.6%: EM #4-1, #4-2, #7-3）と「算定漏れは測られていない領域」（EM #4-4）。一般診療所の常勤事務職員の平均年収は334万1,410円（条件付き: EM #1-1）。紹介手数料の総額は2024年度1,139億円（国会答弁: EM #5-2）。

提出先: Built with Claude: Japan 2026（締切 2026-11-08 20:00 JST）。審査基準: インパクト30（当事者か・日本特有か・問題設定が正しいか・ハッカソン後も使えるか）／デモ25（冒頭の明確さ・前提知識なしで理解・最後まで見たくなる）／Claude活用25（創造的か・他ツール/モデルとの組み合わせ）／深さと実行20（利用者を考えた丁寧な設計と実装をリポジトリで見る）。審査員はリポジトリの中身を読む。

## 3. 決定事項

### 3-1. 設計思想・差別化

1. AIは算定の正否を決めない。正否は決定的なルールエンジン（点数・背反・算定条件、テスト可能）が出す。
2. Claudeが担うのは、略語候補の提示・医師への質問文の生成・新人への筋道と理由の説明・査定通知からのルール候補起草・解説。判定結果を上書きしない。
3. 差別化は4点に絞る: ローカルルール（県差）／ルールの賞味期限／再審査結果の取り込み／答えを出さない設計。「学習する」は言わない。
4. 「エスカレーションが知識になる」は「出所と期限の付いた知識」として語り、「学習する」とは言わない。
5. 価値の中心は新人の独力化。採用・離職への効果は主張しない仮説として検証対象に置く。
6. 独り立ちまでの期間を KPI にしない。

### 3-2. 知識モデル（医事コンテキスト）

7. 知識は4層（制度／地域／ベテランの判断／院内）で管理し、層ごとに生成・減衰ルールを分ける。
8. 院内ローカルルールはシステムに保持するが、新人への助言には使わない。
9. 院内ローカルルールはヒットしなくなったら廃棄提案を出し、人が可否を決める。廃棄提案は手段であり、価値そのものではない。
10. 知識は開かれていることを正とし、**可視性に承認ゲートを置かない**。候補は生成した瞬間から全員に見え、「未検証」ラベルが付く。
11. ベテランの検証は**状態**を変える（未検証→承認済み）。これが別チャットの「ベテラン検証ゲート」の実装。
12. 返戻は即ルール候補を生成する。
13. 査定は必ず知識化するが、再審査申出中は contested 状態にし、結果確定（原審どおり／復活）で承認済みか保管にする。復活した場合は「この項目は認められた」という地域知識にもなる。
14. 再検証のトリガーは ①診療報酬改定（偶数年6月1日）②支払基金の改選（奇数年6月1日、国保連は都道府県ごと）③N=180日ヒットなし（初期値、運用で調整）。
15. 改選日だけでルールを無効にしない。状態は「要再検証→停止→保管」と遷移させ、適用期間・版・廃止理由を残す。
16. 「審査者によって判断が違うという現場の声はあるが、誰も測っていない。だから自分で可視化する」を採用表現とする。
17. 個人名はデフォルトで出さず、知識はチームの共有知として扱う。本人向けの名前表示はオプトイン。
18. 知識の実体は `knowledge/<layer>/<slug>/SKILL.md` ＋ サイドカー `meta.json`（layer / status / source_event / valid_from / review_by / hits / misses / retired_reason）。
19. 承認済みのSkillだけを `.claude/skills/` に決定的スクリプトで同期し、それ以外の状態はロードさせない。同期先もコミットする。
20. 知識ディレクトリはgitで管理し、育った履歴を `git log` で見せる。

### 3-3. メンター・キャラ・体験

21. メンターは一人一セッション（Agent SDK）。キャラと本人のレベルで振る舞いが変わる。
22. ベテランのメンターは別セッションとし、ベテラン本人への問いはそのメンター経由でのみ届く。
23. エスカレーションで解けた案件は「ベテランの判断」層の候補になり、承認済みになれば次からは新人のメンターで止まる。
24. 3キャラは男性3名。本人が自分で選ぶ（質問による振り分けはしない）。
25. 伝え方のタイプは本人の自己申告を任意入力として受け付ける（16タイプ等）。診断はしない。
26. 3キャラにはそれぞれ静止画の立ち絵を用意し、表情を6パターン（通常／笑顔／考え中／驚き／困り／称賛）持たせる。アニメーションはしない。
27. 「困り」は新人の誤りに対して出さない。出すのはカルテ不足（医師側）と審査が難しい場面だけ。
28. 表情の切り替えはメンター出力の構造化フィールド `expression`（enum）で決める。
29. 画像は1キャラ1枚のキャラクターシート（6表情をグリッドで1枚）として生成し、スクリプトで分割する。生成はGemini、自作素材として公開リポジトリに含める。
30. 音声は初回登録と節目（月次提出完了など）のみ。算定作業中はテキスト。
31. 初回登録の音声は ElevenLabs Agents（LLMにClaudeを指定、3キャラ分の声をライブラリから選定）。会話結果（選んだキャラ・呼び名）はクライアントツールでアプリDBへ書く。
32. 医療事務本人のレベルは処理件数の累計で Lv.1〜10。表示は本人画面の端に小さく、他人のレベルは見せない。
33. レベルの主な表現はメンターの振る舞いの変化（ヒントが短くなる／先に出さず聞かれたら出す／呼び方・口調が対等に寄る）。一定レベル以上で他の医療事務のメンターからの質問が届く。
34. レベル名は職位や評価を連想させる語にしない。
35. 既定の表示は「余白が欲しい」多数派向け（レベルは端に小さく、金額は出さない）。やり込みたい少数派はオプトインのトグル1つで詳細（防いだ額、ルール貢献数）を開く。
36. キャラが喜ぶのは「知識が増えた／承認された／連続正解／月次完了」の正方向のみ。チーム単位の空気・機嫌の指標は持たない。

### 3-4. 医師確認（F1・F3）

37. AHIMA/ACDIS 2026年版の7要件をUI要件にする: ①臨床指標を引用 ②誘導しない ③選択肢に「その他」「判定不能」を必ず含める ④点数・金額に触れない ⑤AIが作った質問も同じ基準 ⑥記録を保存 ⑦未回答ならエスカレーション。2022年版は引用しない。
38. 日本語の呼び名は「医師確認」で統一。日本に制度名がない空白に米国基準を先取りして当てる、という位置づけ。
39. 最終承認は医師が行う（医師法24条、医政発第1228001号）。UIは確認ボタン＋承認者名・日時のログ。電子署名は非スコープ。
40. 未回答時は翌営業日にリマインド、3営業日で保留（算定しない）。無床クリニックは院長＝唯一の医師が多い前提。
41. 記録は `query-log/` にMarkdown＋JSON併記、1質問1ファイル。
42. 「聞く」はカスタムツール `ask_missing(target, field, why)` で強制する。宛先が医師ならF1、医療事務ならF3。
43. 代行入力後の医師確認ステップをUIに必ず挟む。

### 3-5. 防いだ額（F9）

44. 「防いだ」＝提出前にルールエンジンまたはF4が指摘し、提出までに本人が修正した項目。本人の自己申告は数えない。表示は常に「推定」と付ける。
45. 金額換算は点数×10円。公費・自己負担の内訳は分けない。
46. 「取りこぼしを防いだ（算定漏れ）」と「差し戻しを防いだ（返戻・査定リスク）」の2系統で集計する。
47. 医師の記載が原因でF1経由で解決した項目は「医師記載起因」として別集計し、事務長→医師へのフィードバック素材にする。
48. 「多く取る」方向の表示・誘導は一切入れない。フレームは「正しく取る・取りこぼさない」。
49. 本人向け表示はオプトイン。ランキング・ノルマにしない。ゲームのスコアは件数・連続正解で、金額は補助として小さく出す。
50. 見逃した額（返戻になった額）は本人向けには出さず、事務長向けに集計のみ出す。
51. 事務長KPIは評価制度に接続しない。

### 3-6. デモ条件（合成レセプト）

52. 診療年月は2025年3月、点数は2024年度改定後。READMEには「2024年度改定後（2025年4月のDX加算改定前）」と書く。
53. 医療機関は在宅療養支援診療所（機能強化型以外・病床なし・東京都）。
54. 症例はK1〜K6の6件で、全件同じ架空クリニックの同じ月のレセプト。UKEは審査支払機関ごとに1ファイル、計2本（国保連用K1〜K5 IR=2／支払基金用K6 IR=1）。症例を足すときは先にEM §5-1の表に行を足す。
55. K1（主症例）は合計14,819点。包括的支援加算150は付けない（重症区分）。C101 650は通則2により付けない。
56. K2は合計6,253点（在医総管3,685＋移行早期100＋包括的支援150＋処方箋料60、HOTなし）。EM §5-1 の6,193点に、EM #7-6 に基づき F400 処方箋料60を足した。特定疾患処方管理加算は主病が糖尿病・高血圧のため付けない（2024改定で対象外）。第2シナリオはK2に統合済み。
57. K6は社保（支払基金、IR=1）に変更し、再検証トリガーは2025年6月1日改選とする。
58. 新人が間違えやすい13項目（レポートA項目21）をルールエンジンのテストケースにする。
59. 略語6例の配置はK3=PD、K4=AF、K1=DM・HOT、K5=CVポート、K2=カテ交換（尿道カテ交換、J063はC002に包括）。
60. レセ電コードは架空とし、READMEに「架空コード」と明記する。
61. UKEは記録条件仕様 令和6年6月版に準拠。Shift_JIS・CSV・CRLF・EOF(0x1A)、IR→(RE→HO/KO→SY→SI/IY/TO/CO)×n→GO。
62. 入力はUKE＋合成カルテ（SOAP）＋受給者証情報。施設届出と過去月は設定ファイルで固定値。
63. K3〜K6の算定明細はdesign-loopの起草工程で作る。K3のC001は月12回で仮置き。
64. 現場描写はインタビューとEMの具体例に限定し、自分で現場例を創作しない。

### 3-7. 技術

65. ランタイムはClaude Agent SDK（TypeScript）をNext.jsのAPI Route内で動かす。Pythonは使わない。
66. 推論の課金は開発＝ハッカソン付与のMax 5x、ランタイム＝$500 APIクレジット（`ANTHROPIC_API_KEY`）。
67. ルールエンジンとライフサイクル判定はTypeScriptの決定的ロジック。LLMに判定・減衰を任せない。
68. メンターのツールは `query_skills / query_history / ask_peer_mentor / ask_human / ask_doctor / ask_missing`。
69. DBはSQLite（Drizzle）。データは全て合成。
70. UIはNext.js自作。職場チャット風（人同士の場）＋算定画面＋医師画面＋事務長レポート。
71. 評価はprompt-eval超軽量版10ケース（理由があるか／医療判断していないか／7要件を満たすか）。

## 6. 検討済み・却下

- 別チャット D24「AI同僚は1体・職場チャットに同居」: 3キャラは役割分担ではなく伝え方の違いで、本人が選ぶことがゲーム性の核。個別メンターは「全体チャットで聞くのが恥ずかしい」への回答。
- 別チャット D26「チームの空気メーター・共有が増えるとAI同僚が喜ぶ」: チーム単位でも裏返しが圧になり心理的安全性と逆行する。
- 別チャット D25の「検証ゲート」を可視性のゲートとして実装すること: 知識は開かれているのが正。状態ラベルで表現する。
- 別チャット U1「3症例のみ」の動画構成を確定扱いにすること: 声とレベルを含めて再協議する。
- EM §6-5「1患者で一気通貫」の動画: 各機能が1症例に詰め込まれて不自然。
- 「紹介手数料を払ってまた採る」を医療事務に当てはめる語り: 医療事務は紹介料を払ってまでは採らない職種（EM #5-5）。払う側として見た職種間の差として語り直す。
- 「医事一人あたり月30万円の算定漏れ」: 公開統計に裏付けなし。
- 「審査員が変わると通らなくなる」の断定: 因果の直接証拠なし。
- 電話で登録完了・音声会話: 日本番号取得が期日内に終わらない。
- 事前生成mp3のみの音声: 名前の呼びかけが動的。
- Gemini Live API / OpenAI Realtime: 声が選べず、脳がClaudeでない。
- 「うちだとこうですよ」と院内ルールを提示する助言: 新人が盲目的に押し、一人前にならない。
- ベテランの処理履歴を本人のメンターだけに閉じる: 知識は開かれているのが正。
- 伝え方3問でキャラを振り分ける: 自分で選ぶほうがゲームとして正しい。
- ベテランの名前を知識に残す: 「名前が残る＝責任を問われる」が多数派。
- 独り立ち期間をKPIにする: 5日では測れない。
- Slack実連携: 準備で時間を食い、動画はUIを撮るだけ。
- 本物UKEの完全パース・実コード使用: 5日では事故る。架空コードと明記。
- 「教育」「学習」「学ぶ」「教える」の語で対外説明: 禁止例との距離を縮める。
- 2022年版AHIMA/ACDISガイドラインの引用: 2026年版に更新済み。

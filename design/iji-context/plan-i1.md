# I-1 の実装計画（2026-11-24 承認）

spec.md FR-202 の I-1：査定・返戻の記録と UKE を決まった規則で突き合わせる道具と、社内テストの手順書。合成の記録で通ることを受け入れ条件とする。振り分けは「直接」（設計ループなし。判定を変えない報告）。入力の形式は sources/research/zogen-henrei-format.md。

## 何を作るか
1. **読み取り**（src/review/ 新設）
   - 増減点連絡書 CSV（`RIzogn…csv`）と返戻内訳書 CSV（`RIhenr…csv`）を読む。項目の並びは資料1 の項目表どおり。文字コードは未確認なので、UTF-8 として正しく読めなければシフト JIS で読む（Node の TextDecoder）。
   - 「請求内容」「補正・査定後内容」の文字列は書式が未確認なので、中を分解しない（そのまま持つ）。
   - 返戻レセプト（RECEIPTC.HEN／SAH）は今回読まない（後述）。
2. **請求への当て方**（決まった規則だけ。AI は使わない）
   - 増減点連絡書の 1 件 → 提出した UKE の 1 請求：医療機関コード＋請求月（ファイル名の処理年月から）＋レセプト番号で当てる。取り込んだ UKE が複数の送信回にまたがって番号が重なるときは「当てられない」にする。
   - 当てた請求の中の行：査定の文字列が、その請求の行の名称（基本マスターの名称）を 1 つだけ含めば、その行に当てる。0 個か 2 個以上なら、医療事務がその請求の行から選ぶ（選択肢に「その他」「判定不能」）。
   - 返戻内訳書はレセプト番号を持たないので、保険者番号＋患者氏名＋診療年月で当て、1 件に決まらなければ人が選ぶ。
3. **事前に指摘できたか**
   - 当てた請求を、測る時点の版で点検し直し、当てた行（または請求）に指摘（確定・条件つき・P 系）があったかを見る。報告に点検のコードの指紋と版を書く（提出の時点の点検結果は残していないため）。
4. **見逃しの理由**（測る前に固定。人が選ぶ。AI に分けさせない）
   - 指摘していた／データがない（カルテ・構造化データ・患者の情報）／決まりを作っていない／人に聞く事実がない／審査の医学的な判断（事由 A など。規則にできない）／突き合わせられない／その他／判定不能
   - 事由記号（A・B・C・D・F・G・H・K。資料1 別表6）は記録して、件数を事由ごとにも数える。記号から理由を自動で決めない。
5. **報告**
   - 件数（全体・事由ごと・理由ごと・指摘していた件数）と、点数の合計は出さない（点数・金額に触れない現場の約束ではないが、I-2 で割合を語らないため件数だけ）※要確認
   - 再審査で戻ったもの（復活）は人が印を付けて除く（SAH を読むのは後）。
6. **画面**：事務長とベテランだけ。取り込み → 当てられなかったものを選ぶ → 理由を選ぶ → 報告。取り込んだファイルは FR-168 の消し方で消せる（アップロード 1 回の単位）。
7. **手順書**：docs/ に社内テストの手順（どこから CSV を取るか、期間〔帳票は 12 か月で取れなくなる〕、AI に送らない、件数だけ持ち出す、消して記録を残す、院長の同意）。
8. **合成の記録**：fixtures/review/ に合成の増減点連絡書・返戻内訳書（既存の合成 UKE の請求に当てる）。文字列の書式は未確認なので、合成であることと書式が推測であることを README に書く。

## 何を捨てるか
- 返戻レセプト（HEN／SAH）の読み取り、再審査等支払調整額通知票、国保連の再審査の形式（今回は人の印で代える）
- 査定の文字列の分解（書式が分かるまで）
- UKE の「請求情報」にレセメンの ID を入れる当て方（レセコン次第で未確認）
- 提出の時点の点検結果の保存

## 危ないところ
- 査定の文字列の書式が分からないまま、名称の含みで当てている。実物で 0 個・2 個以上が多ければ、人の手間が増える
- 「測る時点の版で点検し直す」ので、提出の後に足したルールで「指摘できた」に数えてしまう。報告にそれを書き、版の日付で分けて数える
- 実在の患者氏名を当てに使う。AI には送らない。画面とログに出す範囲は FR-165〜169 に従う

## 受け入れ条件（呼び出し側が再現できる形）
- 合成の増減点連絡書・返戻内訳書を取り込むと、全件が請求に当たり、名称が 1 つに決まる行は自動で、決まらない行は選ぶ欄に出る
- 指摘のある行の査定は「指摘していた」、ない行は理由の選択を求められる
- 報告の件数が合成の正解の表と一致する（テスト）
- 文字コードがシフト JIS と UTF-8 の両方で読める（テスト）
- 取り込んだファイルを消すと、作った記録が残らない（FR-168 の全表走査のテストに足す）
- typecheck・テスト・build・各検査が 0

## Fable の見立てで直すところ（2026-11-24）
1. 「行に指摘があった＝指摘していた」としない。人が「同じ論点／別の論点／指摘なし」を選ぶ。確定と条件つきは分けて数える
2. 版のない診療年月は「版がなく対象外」として分母から外す。今の版で判定できるのは 2026年6月診療分から
3. 請求への当て方：キーに審査支払機関（ファイル名）を足し、氏名と保険者番号で検算し、合わなければ「当てられない」。カルテ番号等が両方にあれば先に使う。前の行の値を引き継ぐ省略規則に従う
4. 行への当て方：NFKC で正規化して最長一致、箇所1 で絞る、行でなくコード単位。合計行と事由 F・G・H は請求単位。自動で当てた分も人が 1 回確かめる
5. 測り直し：記録を見る前に点検のコードの指紋を固定し、見たあとに直した分は別の回として数える（版の日付で分けるのではなく）
6. 理由の一覧を「結果」（同じ論点で指摘していた／別の論点／指摘なし）と「指摘しなかった理由」（データがない／決まりがない／決まりはあるのに当たらなかった／人に聞く事実がない／医学的な判断／その他／判定不能）に分け、複数当たるときの優先順を決める。対象外（版がない・突合点検・保険者の再審査による後日の査定・紙分・当てられない）は報告に別に書く
7. 受け入れ条件に当たらない側の合成（番号の重なり、氏名の不一致、名称 0 個・2 個以上）を足す

## 利用者の判断（2026-11-24「おすすめどおりで承認します」）
1. 数える単位：増減点の明細の件数を主にし、レセプトの件数を並べる
2. 点数：件数を主にし、減点の点数の合計は社内の報告にだけ並べる。割合は出さない（§5 の「※要確認」はこれで決まり）
3. 期間：2026年6月診療分から（spec FR-202 を直した）
4. 実物 1 か月分の UKE で、カルテ番号等・請求情報が埋まっているか、社保と国保で UKE が分かれるかを利用者が手元で見る。結果を待たずに、当て方は両方に備えて作る（カルテ番号等があれば先に使い、なければ審査支払機関＋請求月＋レセプト番号で当てて氏名と保険者番号で検算）。結果で順を直す
4. の結果（2026-11-24 利用者の確認）：社保と国保で UKE は分かれている → 当てるキーに審査支払機関を必ず入れる（計画どおり）。カルテ番号等・請求情報が埋まっているかは未確認
5. 利用者の確認（2026-11-24）：カルテ番号等は全レセプトに入っていて重ならない。請求情報はどのレセプトも同じ値で、当てには使えない → カルテ番号等を先に使う今の作りのままでよい

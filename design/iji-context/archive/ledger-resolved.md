### 指摘

- [C-1] 種別: 設計 / 深刻度: high
  - 指摘: §2-4 で「点数表は report-A 項目21 の点数セットだけから起こし、表にない区分が来たら例外にする」と決めている。この規則のせいで、§7 の完了条件 #1・#2 が満たせない。
  - 破綻シナリオ:
    1. K2（6,193 点）の内訳は 1,776＋3,685＋**100（在宅移行早期加算）**＋150＋482（検査）。在宅移行早期加算（C002 注4、100 点）は report-A 項目21 の点数セットにない（出典は report-B の 187 行目と EM §5 の K2 行だけ）。そのため `evaluate(K2)` は合計を出す前に例外を投げ、§7 #2 の `evaluate(K2).total === 6193` が落ちる。R14 の違反ありフィクスチャ（移行早期加算を正しく付けた行）も同じ理由で作れない。
    2. 違反ありフィクスチャには、点数セットにない区分を含めないと再現できないものがある。R05（特定疾患療養管理料・生活習慣病管理料・創傷処置・喀痰吸引・導尿・在医総管 注2 +300）、R11（外来迅速検体検査加算）、R12（医療情報取得加算・医療DX推進体制整備加算）。どれも `lines` に入れた時点で例外になり、ルールが評価されない。§7 #1 の「違反あり・違反なしの 2 本ずつ」のうち、少なくとも R05・R11・R12 の違反ありが作れない。これらの点数は EM にもないので、表に足すこともできない（「EM の採用値だけを使う」制約）。
  - 提案: 点数表の出典を「report-A 項目21 ＋ EM §5 の K2 行（移行早期 100）」に広げる。点数がわからない区分は「点数不明」として `findings` の判定には通す。合計は「点数不明の区分を含む場合だけ例外（または `total: null`）」と、判定と合計の失敗を分ける。あわせて FR-04（K1 に 150 と C101 650 を付けない）を確かめるテスト（K1 にこの 2 行を足すと R02・R04 が出る）を §7 に明記する。

- [C-2] 種別: 設計 / 深刻度: high
  - 指摘: §4-3 のトリガー判定は、遷移表（§4-2）と組み合わせると 2 通りに壊れる。(a) idle の起点を「`last_hit_at`、なければ `status_since`」としている。(b) 同じ知識に 2 つのトリガーが同時に立つ場合を扱っていない。
  - 破綻シナリオ:
    - (a) 地域層の知識で `last_hit_at`=2025-01-01。idle で 2025-07-01 に要再検証になる。ベテランが 2025-07-10 に再確認（`RECHECK_PASS{veteran}`）して承認済みに戻る。次の `evaluateTriggers` では `last_hit_at` が 180 日より前なので idle が即座に発火し、要再検証に戻る。停止中の知識をベテランが `DISPOSAL_REJECT` で承認済みに戻した場合も同じで、FR-45 の「ベテランの再確認」と「廃棄提案の却下」が実質的に無効になる。
    - (b) 支払基金・地域層の知識が 2024-11-01 に承認済みになり、ヒットがない。now=2025-06-01 で ②改選と ③idle（181 日）が両方発火し、同じ知識に `TRIGGER` が 2 件返る。呼び出し側が順に `transition` を通すと、2 件目は「要再検証 × TRIGGER」になる。これは表にない組み合わせなので例外になり、バッチが途中で止まる（どこまで書いたかの扱いも書かれていない）。
  - 提案: idle の起点は `max(last_hit_at, status_since)` にする。`evaluateTriggers` は 1 つの知識につき最大 1 イベントを返す（どのトリガーを優先するか、理由を `history.event` にどう残すかを決める）。§7 #4 に、この 2 つの回帰ケースを足す。

- [C-3] 種別: 設計 / 深刻度: medium
  - 指摘: `HIT`（同じ条件で問題なく通った）を出す入口と、評価したときに当たった知識を提出結果に結びつける記録が、設計のどこにもない。このため `hits`・`last_hit_at`・`RECHECK_PASS{claim}` には、システム上の生産者がいない。
  - 破綻シナリオ: §4-4 は「評価時に `matches` を判定し、提出結果を取り込むときに HIT／COUNTER_EXAMPLE を決める」としている。しかし §6 の入口は「返戻・査定・再審査の取り込み」だけで、「問題なく通った」を表すイベントがない（実際の提出は非スコープ。現実でも、通ったことは連絡がないことでしかわからない）。さらに、評価時にどの知識がどのレセプトに当たったかを保存する場所もない（知識はファイルで管理し、DB には置かない方針）。結果として、`hits` は永遠に 0 のままになる。地域・ベテラン・院内の知識は 180 日たつと必ず要再検証になり、さらに 180 日で必ず停止する。FR-45 の「次の請求で同じ条件が通った」という復帰経路には到達できない。単体テストでは `HIT` を手で注入すれば通ってしまうため、§7 では検出できない。
  - 提案: 「提出結果の取り込み」を `LifecycleEvent` の入口として明記する。デモでは「月次提出完了」で、返戻・査定がなかったレセプトを一括で HIT 扱いにするなどの方法がある。評価時のマッチ結果（レセプト ID × 知識 ID）をどこに保存するかも決める。あわせて、ヒットのたびに `knowledge/*/meta.json` を書き換えると FR-49 の `git log` がカウンタ更新で埋まる問題も扱う（ヒット数だけ DB 側に分ける等）。

- [C-4] 種別: 設計 / 深刻度: medium
  - 指摘: `events` に事実がないとき、それが「起きていない」のか「わからない」のかを区別する方法が決まっていない。一方で「事実がないなら情報不足を返す」と「K1 の findings が空」の両方を要求しているため、矛盾する。
  - 破綻シナリオ: K1 の `events` には、退院日も在医総管の算定開始月もない（主症例の設定に退院の記述がない）。R14 は「事実がないので推定しない」に従って `情報不足` を返し、K1 の findings が空でなくなって §7 #2 が落ちる。逆に「ない＝起きていない」と読む実装にすると、K2 で退院日を書き忘れたフィクスチャでも R14 が黙って通過し、FR-36（`ask_missing`）に流れるべき確認が消える。R09（死亡）・R10（往診）・R13（別表第七）も同じ分かれ目にある。
  - 提案: `ClaimContext` のフィールドごとに既知か不明かを明示する（例: `dischargeDate: string | "none" | "unknown"`）。各ルールが「不明」のときだけ `情報不足` を出すようにする。K1 のフィクスチャでは全項目を既知として埋める。

- [C-5] 種別: 設計 / 深刻度: medium
  - 指摘: 同期の出力先を `.claude/skills/iji-<layer>-<slug>/SKILL.md` にしているが、`layer` の値が日本語（"制度" 等）である。また SKILL.md の frontmatter（name/description）を誰が生成するかも決まっていない。このため、同期した Skill がメンターに読み込まれないおそれがある。
  - 破綻シナリオ: `iji-制度-...`・`iji-地域-...` というディレクトリ名と name ができる。Agent Skills の name は「英小文字・数字・ハイフンだけ」で、親ディレクトリ名と一致する必要がある（仕様の記憶に基づく。ローダーが黙って無視するか、エラーを出すかは未確認）。slug も日本語なら同じ問題が起きる。§3 は「SKILL.md は説明だけを持つ」としており frontmatter に触れていないので、そのままコピーすると description がない Skill になり、`query_skills` やメンターから見つからない。副次的な問題として、§7 #6 の「`git status --porcelain` を 2 回実行し、2 回目で差分ゼロ」は、HEAD との差を見るコマンドである。1 回目の未コミットの変更が 2 回目にも残るため、冪等性を確かめる条件として成り立たない。FR-48 の「同期先もコミットする」も手順に入っていない。
  - 提案: 層は ASCII のコード（`seido`/`chiiki`/`veteran`/`innai`）と表示名に分ける。slug は ASCII に限定する。frontmatter は sync が meta.json から決定的に生成する。§7 #6 は「1 回目の出力をコミット → 2 回目の実行後に `git status --porcelain` が空」か、2 回分の出力ディレクトリのハッシュ比較に直す。

### 賛成点（根拠つき）

- 純関数の `transition` に、表にない遷移は例外という方針を組み合わせ、時刻を引数にしている。この形なら、§7 #3 の総当たりで FR-64 の閉じた 6 状態を機械的に保証できる。最も危うい前提は「呼び出し側が `evaluateTriggers` の結果を 1 件ずつ安全に適用できること」で、これは C-2 で崩れている。
- 「指摘があっても合計は変えない」は FR-11 と整合する。report-A の点数セットで K1 を足し直すと 14,819 点、report-B の内訳で K2 を足すと 6,193 点になることを確認した（ただし K2 は C-1 の例外で止まる）。

2. **［Major／設計］制度層が、ヒットなしを理由に停止する。**  
   [design.md:179](/Users/toshixa/Documents/iji-context/design/iji-context/design.md:179)  
   要再検証からの `IDLE_EXPIRED` が「全層」対象です。制度層を改定で要再検証にした後、180日請求がなければ停止・廃棄提案へ進みます。これは FR-66 の「制度層の減衰は改定時だけ」に反します。要再検証中の期限判定にも層別の制約を適用し、この経路を検証対象に加える必要があります。

3. **［Major／設計］`match` では、正常通過と「同じ条件」を判定できない。**  
   [design.md:125](/Users/toshixa/Documents/iji-context/design/iji-context/design.md:125)  
   制度層の照合に使う `ruleId` は `ClaimContext` に存在せず、違反時の `Finding` にだけ現れます。Finding を使っても、正常通過時の適用ルールを識別できません。また、区分番号等だけでは要介護度などが異なる請求を区別できず、誤った再承認・停止につながります。FR-45・47 を満たすには、正常時も含む適用判定と、知識ごとの条件表現を定義すべきです。

4. **［Major／設計］請求結果の再取込みで、再検証を誤って解除できる。**  
   [design.md:186](/Users/toshixa/Documents/iji-context/design/iji-context/design.md:186)  
   結果を請求ID・知識版・処理済み結果IDへ結びつける契約がありません。以前の成功結果を要再検証への遷移後に再取り込みすると、記載どおりの処理では `RECHECK_PASS` となり、「次の請求」で確認していない知識まで承認済みに戻せます（FR-45）。提出時の適用記録、再検証対象となる請求の条件、重複排除を明記する必要があります。

5. **［Major／設計］投稿者による層選択が、固定された生成元を迂回する。**  
   [design.md:147](/Users/toshixa/Documents/iji-context/design/iji-context/design.md:147)  
   F11 の提案では投稿者が層を選べますが、FR-66 は制度層を初期投入、ベテラン層をエスカレーション解決などに限定しています。自由選択を許すと、手動提案から制度層を作り、異なる減衰ルールを適用できます。既存知識への改善提案と新規生成を区別し、生成元と層の組合せを制約すべきです。

## Round 2 — 2026-11-04 — 工程: 批評

対象: design/iji-context/design.md v2
入力: spec.md（FR-01〜04, FR-38〜51, FR-64〜66）、ledger.md、EM、docs/sources/report-A.md「### 21.」、照合用に docs/sources/report-B.md「### 21.」（K2 の出典）
固定前提: U-G〜U-J（FR-43, FR-45, FR-64〜66）は変更を提案しない。以下の提案はすべて、遷移表を変えずに「提出結果をどのイベントに対応させるか」と「データの持ち方」だけを直すもの

### 指摘

- [C-6] 種別: 設計 / 深刻度: high
  - 指摘: §4-4 の「通過→HIT／返戻・査定で区分が重なる→COUNTER_EXAMPLE」という対応は、知識の向き（「こうすれば通る」なのか「こうすると落ちる」なのか）を見ていない。返戻・査定から生まれる知識（地域層の大半と、返戻起点の院内層）はほぼ「こうすると落ちる」型なので、HIT と反例が逆になる。
  - 破綻シナリオ: K6 の流れで考える。2 月分の BNP が「漫然」で査定され、原審どおりになった。これで地域知識「東京都で BNP（D008）を毎月算定するとき、コメントがないと査定される」が承認済みになる（match は `kubunAll:["D008"]`, payer, prefecture）。2025-06-01 の改選で要再検証に落ちる。その後の請求は次のように扱われる。
    (a) 新人がこの知識を無視し、コメントなしで D008 を立てて再び査定された。これは知識が正しいことの再確認なのに、§4-4 では `kubun[]` が `kubunAll` と重なるので COUNTER_EXAMPLE になる。知識は要再検証から停止に進み、正しい知識に廃棄提案が出る。
    (b) コメントなしで D008 を立てたが、たまたま通った。これは知識に対する反例なのに、HIT（要再検証なら `RECHECK_PASS{claim}`）になり、知識は承認済みに戻る。
    (c) 「X と Y を同時に立てると返戻」型の知識（院内層・地域層）では、助言に従って Y を外すと `kubunAll` が成り立たない。このため適用記録が作られず、HIT が一度も付かない。③ idle で要再検証になり、さらに 180 日で停止する。知識がよく効くほど早く消える。
    §7 #5 のテストは「通過で HIT」だけを見るので、この逆転は検出できない。あわせて、§4-4 の「制度ルールの対象区分」はどこにも定義されていない（ルールが持つのは `appliesTo`/`check` だけ）。このため、制度層の COUNTER_EXAMPLE の判定は実装者が勝手に決めることになる。
  - 提案: `KnowledgeMeta` に向き（例 `expect: "pass" | "reject"`）を足し、`source_event.type` から既定値を決める（返戻・査定→reject、再審査復活・初期投入→pass）。`importResult` は「結果が知識の予言どおりなら HIT／RECHECK_PASS、予言に反したら COUNTER_EXAMPLE」と判定する。(c) については、「助言に従った結果、match が偽になった」場合も適用として記録するかどうか（評価前後の lines の差分で判定する等）を決める。制度層は、COUNTER_EXAMPLE の対象を「その請求の findings に当該 ruleId が出ていなかったのに、該当区分が返戻・査定された」と定義する。遷移表（U-H）は変わらない。

- [C-7] 種別: 設計 / 深刻度: medium
  - 指摘: `applications` の表は「算定を確定してエンジンを評価したとき」に追記するだけである。(claimId, knowledgeId) で一意にする制約も、最終版で置き換える規則もない。このため、確定→指摘→修正→再確定の流れ（FR-28、F9 の「提出までに本人が修正」）で、修正前の算定行に対する適用記録が残る。
  - 破綻シナリオ: (1) 新人が確定し、指摘を受けて直し、もう一度確定した。同じ知識について適用記録が 2 行でき、提出結果「通過」を 1 回取り込むと HIT が 2 回付く。resultId による重複排除（§4-4 手順 1）は結果の二重取り込みしか防がないので、効かない。(2) 修正前の lines にだけ X・Y が両方あり、院内知識 `kubunAll:[X,Y]` が当たった。修正で Y を外して提出したところ、X が査定された。提出したレセプトにはこの知識が当たっていないのに、残った古い記録から COUNTER_EXAMPLE が出る。知識が要再検証なら停止に進む。§7 #5 は同じ resultId の二重取り込みしか見ていないので、どちらも検出できない。
  - 提案: `applications` を (claimId, knowledgeId) で一意にし、再評価のたびにその claimId の行を全部置き換える（最後の評価＝提出版にする）。あるいは「提出確定」という明示的な操作のときだけ記録する。§7 #5 に「再確定 2 回→通過 1 件で hits は 1」と「修正で外れた知識には結果イベントが出ない」を足す。

- [C-8] 種別: 設計 / 深刻度: medium
  - 指摘: §3 は層ごとに match の必須項目を決めている（制度＝ruleId、その他＝kubunAll）。ところがこの規則が、§4-1 の生成元表、§3 自身の「院内メモ」の逃げ道、§4-3 のトリガー②の 3 か所と噛み合っていない。
  - 破綻シナリオ: (1) F6 のエスカレーションで、K3 の「カルテの PD は、処方（マドパー）と受給者証 54 から判断してパーキンソン病と読む」がベテランに解決された。この判断は区分の組み合わせでは表せない。§3 はこうした知識を「院内メモ（match なし）」に回すとしている。しかし §4-1 は、エスカレーションからは「ベテラン層しか作れない」とし、§3 の store は「ベテラン層は kubunAll が必須」として拒否する。院内メモにする経路も、ベテラン層で作る経路も塞がっているので、知識は作れない。FR-15（エスカレーションで解けた案件はベテラン層の候補になる）が守れず、ベテランの判断がメンターに届かない。仮に院内層で作れたとしても、FR-12 により助言には使われない。さらに、store は院内層にも kubunAll を必須としているので、「match なしの院内メモ」自体を書き込めない。(2) 地域層では `payer`・`prefecture` が省略できる。返戻から payer なしの地域知識ができると、§4-3 のトリガー②でどの改選日（支払基金の奇数年 6/1 か、国保連の都道府県別か）を使うかが決まらない。結果は実装者しだいで、「発火しない」か「支払基金の日付で発火する」かに分かれる。§7 #4 はこの場合を見ていない。

- [C-9] 種別: 設計 / 深刻度: medium（X-1 の対応が不十分なための再提起。新しい根拠は以下）
  - 指摘: v2 の読み出し側の防御は、メンターの `query_skills` だけにかかっている。しかし Agent SDK は `.claude/skills/` の Skill をセッション開始時に読み込み、モデルが自分で呼び出す。この経路は `query_skills` を通らない。さらに、`query_skills` が `knowledge/` を直接読むなら、除外条件に「院内」が入っていない。
  - 破綻シナリオ: (1) FR-10 では、メンターは医療事務 1 人につき 1 セッションで、長く続く。セッションの開始後に、K6 の地域知識が改選で要再検証になった。同期は `.claude/skills/iji-regional-…` を消すが、すでに起動しているセッションの Skill 一覧にはこの Skill が残る。モデルはこれを根拠に助言でき、FR-48 の「それ以外の状態はロードさせない」に反する。ファイルが消えた後に呼ばれたときの挙動は、仕様の記憶に基づくため未確認。(2) §5 は「`query_skills` が `knowledge/` の meta.json を読み、承認済みでないものを除く」としている。結果の母集合を `knowledge/` から取る実装だと、承認済みの院内知識がそのまま返り、FR-12 に反する。
  - 提案: メンターのセッションでは、Skill の自動ロードを無効にして `query_skills` だけを入口にする。それができない場合は、同期のたびにセッションを作り直す（または Skill 一覧を再読み込みする）ことを契約に書く。`query_skills` の除外条件に「layer !== 院内」を明記する。§7 #8 に「承認済みの院内知識は `query_skills` からも返らない」を足す。

- [C-10] 種別: 前提 / 深刻度: low
  - 指摘: P-1 は「K2 に処方箋料がないのは届出の前提が違うから」としている。しかし report-B「### 21.」は、理由を「C002 の投薬包括により処方箋料も別加算しない」という算定ルールとして書いている。つまり report-A（K1 は F400 60＋56＋10 を算定）と report-B は、在医総管の月に処方箋料を別に算定できるかで食い違っている。R05 の包括範囲がどちらに従うかは設計に書かれていない。

  - 提案: R05 の包括リストは「report-A 項目21 のテストケース 5 に列挙された項目に限る（F400 は含めない）」と明記する。P-1 の記述も「report-B は処方箋料を包括と解しているが、本設計は report-A を正とする」に直す。どちらが正しいかを留意事項通知で確かめるかどうかは、ユーザーに確認する。

## round-2（codex）— 原文は reviews/round-2-codex.md

重大度順に5件です。いずれも設計上の指摘です。

1. **高／設計：修正前の適用記録で再承認できる（X-4の対応不足）**  
   [§4-4](/Users/toshixa/Documents/iji-context/design/iji-context/design.md:227) は結果を `claimId` だけで適用記録に結びつけます。確定後に算定行を削除・再確定しても、古い記録を失効させる規定がなく、削除前に適用した知識を提出結果の「通過」で再承認できます。状態・`status_since` の照合では防げません。FR-45 の「同じ条件」を保証するため、提出版と、その版の適用記録を結びつける必要があります。

2. **高／設計：表現できない査定知識をライフサイクルから外している（X-3の対応不足）**  
   [§3](/Users/toshixa/Documents/iji-context/design/iji-context/design.md:152) の `match` は訪問回数・日付関係・処方種類数などを表現できず、表現できない知識は `meta.json` のない院内メモに留めます。これでは、例えば訪問回数を理由とする査定を地域層の候補として生成・検証できません。FR-42・43・66 に反します。条件を保持できる形式と、未対応条件でも元の層の候補として残す経路が必要です。

3. **高／設計：査定取込後の再審査申出を扱えない**  
   [§4-2](/Users/toshixa/Documents/iji-context/design/iji-context/design.md:185) には、未検証・承認済みから `contested` に入る遷移がありません。査定を申出なしで取り込んだ後、再審査を申し出ると、FR-43 の「申出中は contested」を満たせません。取込JSONにも申出状況がありません。申出イベントと、既存の査定知識を対象にした遷移を定義する必要があります。

4. **中／設計：知識の版と適用記録を結びつけられない**  
   [§3のメタデータ](/Users/toshixa/Documents/iji-context/design/iji-context/design.md:134)にも適用記録にも版の識別子がなく、`history` は状態遷移だけです。同じ知識IDの本文を改訂すると、過去の請求がどの本文に基づいたか確定できません。FR-45 の版保存を満たすため、版IDまたは内容ハッシュを保存し、適用記録にも記録する必要があります。Git管理だけでは、この対応関係は定まりません。

5. **中／設計：ヒットなしで停止した院内知識から廃棄提案が出ない**  
   [§4-2](/Users/toshixa/Documents/iji-context/design/iji-context/design.md:196) は反例による停止にだけ廃棄提案を付け、`IDLE_EXPIRED` による停止には付けていません。記載どおり実装すると、使われなくなった院内知識が停止しても人の判断に回らず、FR-46 を満たしません。idleによる停止にも廃棄提案を生成する副作用が必要です。



C-6〜C-9・X-6〜X-10 は design.md v3 で対応（未批評）。C-10 は ledger.md の未解決に全文。

# 連携（コネクタ）

電子カルテ・レセコンとつなぐための境界と、読み取りコネクタの説明（spec FR-104〜115）。
**接続先は環境変数の許可リストだけ。既定で無効。** 同梱しているつなぎ先は模擬サーバー（合成データ）だけで、コネクタを呼ぶ画面や API はまだない（境界とコネクタと、読んだ患者を患者マスタへ入れる処理だけがある）。
画面から使える連携は、UKE のアップロードだけ（下の「UKE のアップロード」）。

## 境界の 3 つの型（`src/connect/types.ts`）

| 境界 | 返すもの | 持っているコネクタ |
|---|---|---|
| `PatientSource` | 患者基本情報 `ConnectorPatient`（接続先での患者の id ＋ 患者マスタに取り込む形 `PatientRecord`：氏名・性別・生年月日 YYYYMMDD・加入情報 `CoverageInfo` の一覧） | fixture・orca・fhir |
| `ClaimSource` | 診療年月の請求 `ConnectorClaims`（`files` は UKE を読んだときと同じ `UkeFile`、`unmapped` は対応のないコードの行） | fixture・orca |
| `ChartSource` | 診療年月のカルテ記載 `ConnectorChart`（訪問日ごとの記録・処方・傷病名） | fixture・fhir |

`Connector = { id, label, patient?, claims?, chart? }`。持っている能力だけを載せる。書き込みの口はない。

患者と加入情報の型は、患者マスタの型（`src/patient/profile.ts` の `PatientRecord`・`CoverageInfo`）を使う。連携だけの型は持たない（種類は「医保」「公費」、番号は `payerNumber`）。

## 読んだ患者の行き先（患者マスタと患者情報チェック）

`app.checkConnectorPatient(患者, 診療年月)`（`src/server/app/patients.ts`）が、コネクタで読んだ患者を患者マスタに取り込み、UKE から来た患者と同じ患者情報チェック（P01〜P08）にかける（spec FR-123）。

- 同じ人かどうかは、UKE のときと同じ鍵（医保の番号＋生年月日・性別、なければ氏名＋生年月日・性別）で決める。接続先での患者の id は鍵に使わない。
- 記号・番号は、患者マスタに入れる時点で半角にそろえる（全角で返す接続先と、半角の UKE を同じ人として重ねるため）。
- コネクタが負担割合・有効期間を持ってきたときは、医療事務がまだ確かめていない加入情報に限って履歴に 1 行足す（出所は「連携」）。確かめた記録は上書きしない。
- 請求を伴わないので、レセプト種別と診療日を使うチェック（P03・P04 の一部、P06 の診療日との照合）は働かない。
- いまは処理があるだけで、呼ぶ画面・API はない。

- `fixture`（`fixture.ts`）：同梱の合成データ（fixtures/ の UKE・症例・カルテ）。常に有効。通信しない。
- `orca`（`orca.ts`）：ORCA API 形式（日レセ API）。患者基本情報と、その月の請求（診療行為。下の「ORCA の請求」）。
- `fhir`（`fhir.ts`）：HL7 FHIR JP Core 形式。Patient・Coverage と、Encounter・MedicationRequest・Condition の検索。

## コネクタの足し方

1. `src/connect/<id>.ts` に `create<Id>Connector()` を書き、持てる境界だけを実装する。
2. 外へ出る通信は、必ず `connectJson(id, 相対パス)`（`fetch.ts`。JSON でない応答は `connectText`）を通す。`fetch` や `http.request` を直接呼ばない。
3. 応答は zod のスキーマで検査してから境界の型に写す。合わなければ `formatError`（取り込まない）。
4. 通信の形（パス・項目名・スキーマ）と、その出典・未確認の点をファイルの冒頭に集め、模擬サーバー（`fixtures/connect/mock-server.ts`）も同じ定義を使う。
5. `src/connect/index.ts` の `EXTERNAL` に足し、`tests/connect/` に模擬サーバーとの結合テストを書く。

## 設定（環境変数。既定はすべて空＝外部コネクタは無効）

| 名前 | 意味 | 例（架空） |
|---|---|---|
| `RESEMEN_CONNECTORS` | 有効にする外部コネクタの id（カンマ区切り） | `orca,fhir` |
| `RESEMEN_CONNECT_ALLOW` | 接続を許す `host:port`（完全一致・カンマ区切り） | `recept.example.test:443` |
| `RESEMEN_CONNECT_<ID>_URL` | 接続先。WebORCA の `/api` はここに書く。認証情報・クエリは書けない | `https://recept.example.test/api` |
| `RESEMEN_CONNECT_<ID>_USER`／`_PASSWORD` | Basic 認証（ORCA） | Secret Manager から渡す |
| `RESEMEN_CONNECT_<ID>_TOKEN` | Bearer 認証（FHIR） | 同上 |
| `RESEMEN_CONNECT_FHIR_PATIENT_SYSTEM` | 患者番号の identifier system（医療機関コードを含む全体。必須） | `urn:oid:1.2.392.100495.20.3.51.19999999999` |
| `RESEMEN_CONNECT_FHIR_KOHI_SYSTEM` | 公費負担者番号の identifier system | 未確認。既定は仮の値 |
| `RESEMEN_CONNECT_TIMEOUT_MS`／`RESEMEN_CONNECT_MAX_BYTES` | タイムアウト（既定 10 秒）・応答の上限（既定 2 MB） | `10000`／`2097152` |

接続先はリクエストから受け取らない。コネクタ id から、この環境変数だけを引く。

## 通信の守り（`src/connect/fetch.ts`）

防ぐもの：
- 許可リストにない接続先（`host:port` の完全一致。既定は空）。
- https 以外。http は「本番でない・ループバック・許可リストにある」がそろったときだけ（模擬サーバー用。本番ではこの例外を持てない）。
- リダイレクト（従わない）、遅い応答（全体にタイムアウト）、大きい応答（content-length と実際に読んだ量の両方）、content-type・JSON（ORCA の請求は XML）・スキーマの違い。
- 本番での内部アドレス宛て：10/8・100.64/10・127/8・0/8・169.254/16（クラウドのメタデータ）・172.16/12・192.168/16・198.18/15・224/4・240/4、::・::1・64:ff9b::/96・fc00::/7・fe80::/10・ff00::/8。答えの IP が 1 つでも当たれば出ない。
- **DNS リバインディング**：名前解決は 1 回だけで、検査を通った IP にそのまま接続する（`node:https` の `request` に、その IP だけを返す `lookup` を渡す。接続は毎回新しく張る）。ホスト名は元のまま渡すので、証明書の検証・SNI・Host ヘッダは元のホスト名で働く。
- 相手が返した URL（FHIR の next リンク）で、設定した接続先の範囲（同じ origin・同じパスの下）の外へ出ること。
- 認証情報・接続先のパス・応答の本文が、エラーやログに出ること（エラーに載るのはコネクタ id・原因の種類・定型文・HTTP ステータスだけ）。

失敗は `ConnectError` で、`kind` に原因が入る：`config`／`not_allowed`／`redirect`／`timeout`／`too_large`／`format`／`auth`／`upstream`／`network`／`not_found`。

残るもの：
- 本番でない環境では、内部アドレスの検査をしない（許可リストと https の検査、IP の固定はする）。
- 許可リストに載せた相手そのものが内部を中継する場合（相手のサーバーの側のリダイレクトや代理）は防げない。
- 上に挙げていない特殊な範囲（192.0.0.0/24、文書用の 192.0.2.0/24 など）は検査しない。IPv6 に IPv4 を埋め込む形は ::ffff: と 64:ff9b:: だけを見る。
- クライアント証明書（WebORCA クラウド・SSL クライアント認証）には未対応。プロキシ経由の接続にも未対応（環境変数のプロキシ設定を見ない）。
- 相手が正しい形で返した誤ったデータは見抜けない（スキーマは形しか見ない）。

## 対応のないコードの扱い（FR-111）と ORCA の請求

診療行為コードは、診療年月の版が持つ対応表で区分に写す（`src/engine/revisions/` の `codes`・`bundles`。必ず版を決めてから引く）。対応表は実在の診療行為コード（採用値の表にある行だけ。EM §2-8）で、マスター本体は同梱しない。
対応表にないコード、対応先がこのアプリの区分にないコードは、例外にせず `unmapped`（請求 id・コード・日付）に入れ、算定行には入れない。`unmapped` が 1 件以上あるレセプトは「判定の対象外 n 件」と表示し、合計を出さない（表示とエンジン側は後の工程）。
いまあるコネクタは、どれも `unmapped` を出さない（fixture のコードはすべて表にあり、orca は表にないコードがあれば応答ごと断る）。

### ORCA の請求（`orca.ts` の `claims.getClaims`）

患者の id ごとに、診療行為の API（`POST api01rv2/medicalgetv2?class=03`。診療月診療コード情報）を呼び、コードと算定日を算定行にする。この API は、公式仕様で要求・応答とも xml2 形式だけ（`format=json` の記載がない）。

- **受け取るのは、対応しているコードだけ。** 診療年月の版の表にないコードが 1 つでもあれば、`unmapped` に回さず、応答ごと断る（UKE の取り込みと同じ表で引く）。診療年月に当たる版がない月も断る。ORCA コネクタの `unmapped` はいつも空。
- 包括の検査（生化学的検査(Ⅰ)。検査項目のコードが 1 行ずつ返る）は、算定日が同じ項目をひとまとまりとして数え、項目数で区分を決める。4 項目以下は断る（この API には点数・回数の算定単位が載っていない）。
- XML は `fast-xml-parser`（MIT）で読む。設定は安全な側：実体を展開しない、DOCTYPE・実体の宣言のある応答は読まずに断る、値は文字列のまま受けて zod で検査する、属性は読まない、`__proto__`・`constructor`・`toString` などの名前の要素があれば断る。整形式でない XML も断る。大きさの上限（`RESEMEN_CONNECT_MAX_BYTES`）は、XML として読む前に `fetch.ts` で通す。
- 患者・保険は患者基本情報（`patientgetv2`）から引く。医療保険が 1 つに決まらない患者は断る（どの保険で請求したかが、この API では分からないため）。あて先（国保連・支払基金）は、保険者番号から決める（`payerOfInsurer`）。
- この API に載っていないので埋めていないもの：レセプト種別・傷病名・コメント・医療機関の情報・都道府県・請求年月（どれも空）。レセプト種別と傷病名を使うチェックは働かない。コメントは「持たない」請求として渡す（`commentsKnown` が偽）。公費は、患者基本情報にあるものを全部載せる（その月の請求に使ったかどうかは分からない）。
- 回数は「算定した日の数」として読む。同じ日に 2 回以上の算定は、この API の形（日ごとの 0／1）では分からない。包括分の行（`Medical_Class_code` が 1）は、あれば断る。
- 請求 id は「患者の id-診療年月」で作る。患者の id を省いた呼び出しは断る（全件を返す API ではない）。
- 患者病名（`diseasegetv2`）は読んでいない（これも xml2 形式だけ）。

## 模擬サーバー（FR-112）

`npx tsx scripts/mock-connect.ts [ポート]` で 127.0.0.1 に起動する（既定 8799）。認証の値は起動のたびに作られ、アプリに渡す環境変数の形で表示される。
返すのは合成データ（K1・K2・K3・K4。`fixtures/connect/orca.json`・`fhir.json`）だけ。ORCA の診療行為は、症例の算定行を診療年月の版の診療行為コードにして、xml2 形式で返す。この 2 つは、症例と同じ合成データ（`fixtures/uke/patients.json`・`fixtures/cases/`・`fixtures/charts/`）から `npx tsx scripts/gen-connect.ts` で作る（手で直さない。診療年月は `config/demo.json`）。パスの頭に `/fault/<種類>` を付けると壊した応答を返す（`mock-server.ts` の `FAULTS`）。自動テストも同じサーバーを使う。

## UKE のアップロード（FR-106〜109）

`POST /api/uke/upload`（multipart/form-data の `file`。事務・ベテランの役割）。見本は `GET /api/uke/sample?name=…` で取れる。

受け取る条件（1 つでも満たさなければファイルごと断り、何も保存しない。理由は「n 行目：…」の定型文で、ファイルの中の値は返さない）。対応していないコードの行は、断る理由にしない（下の「対応していないコードの行」）：
- 大きさ 1 MB・5,000 行・1 項目 100 文字まで（`src/uke/limits.ts`。値はたたき台）。回数は 1 分 6 回・1 日 60 回まで（`config/limits.json`）。
- Shift_JIS・CRLF・末尾 EOF。レコードの種類・列数・順が記録条件仕様（医科用 令和8年8月版。このアプリが書き出す主要列）どおり。診療行為は点数・回数の算定単位で読む：単位の終わりは点数が書いてある行で、点数の欄は 1 回分、回数と算定日は単位の各行に同じ値。点数の行で終わらない単位、回数・算定日がそろわない単位は断る。
- 数字の項目が数字だけで範囲の中。1 日の回数は 9 回まで。
- 診療年月に当たる版があるレセプトでは、コードがすべてその版の表にある単位は、1 回分の点数が、引いた区分の点数の合計と合う（注加算は基本の項目と合算。包括の検査は項目数で決まる区分の点数）。HO の合計点数・GO の総合計点数が、単位の点数 × 回数の合計（対象外の単位も含む）と合う（合計の検査は、版のないレセプトでも行う）。診療年月に当たる版がないことは、断る理由にしない（下の「版のない診療年月のレセプトと試算」）。
- 傷病名は、未コード化（0000999）なら名称を読み、ほかの傷病名コードはコードを保持する（名称は、同梱の表にある 6 種だけ分かる）。
- 同じファイル（同じ内容のハッシュ）をすでに取り込んでいない。断るのは同じファイルの取り込み直しだけ。

上の条件を通ったものは、見本と違う内容（同じ患者の別の月、同じ患者のレセプトが 2 枚あるファイル、カルテ番号が空のレセプト、国保連あて・支払基金あて）でも受け取る。

**対応していないコードの行は、断らずに「点検の対象外」として残す**（`UkeReceipt.others`）。対象外になるのは、算定の単位ごと：診療年月の版の表にない診療行為コードを 1 つでも含む単位、医薬品（IY）・特定器材（TO）の行を含む単位、包括の検査で項目数が包括になる数（5 項目）に満たない単位・包括の対象でない項目が混ざる単位。対応しているコードでも、対応していない加算と同じ単位に入っていれば、その単位ごと対象外になる（同じ診療識別の下のほかの単位は点検する）。対象外の単位は、コード・1 回分の点数・回数・算定日を UKE に書いてあるまま持ち、名称は持たない（マスターを同梱しない）。

**対象外の単位があるレセプト**（`ClaimContext.partial`）は、行が請求の一部でしかないので、次のように扱う：
- 合計は 2 つ出す：UKE に書いてある請求の合計（HO・KO）と、点検した行の小計。判定の `total` は null で、小計は `subtotal` に別に返す。
- 出す指摘は、ルールが申告した種類（`Rule.soundWhenPartial`。いまある行と確かめた事実だけから言えるもの）だけ：R04 の指導管理料が 2 つ、R05 の管理料と含まれる項目、R06 の対象外の主病、R09 の看取り加算と死亡診断加算、R12 の併算定、R17 の必ず要る記載の記載もれと形式。申告のない種類の指摘は捨て、そのルールを情報不足（「この請求には点検の対象外の行があるため、決められません」）として 1 件返す。
- 申告が正しいことは `tests/engine/partial.test.ts` が縛る（同梱の症例と練習問題の入力から、行を 1 行ずつ・1 区分ずつ対象外に移しても、新しい指摘が出ない）。

**取り込んだレセプトの点検**（`GET /api/uke/claims/<請求 id>/check`。事務・ベテラン・事務長。画面は取り込みの一覧から開く `/uke/<請求 id>`）：UKE に書いてあるとおりのまま（行もコメントも入れ替えずに）判定した結果を返す。コメントを持つ請求として判定するので、摘要欄の記載の点検（R17）が動く。カルテ側の記録は使わない（同梱の見本から取り込んだレセプトでも）。返すもの：UKE に書いてある合計、点検した行と小計、対象外の単位と行数、指摘、記載もれの件数、情報不足、コメントの一覧、患者情報チェックの指摘。何も記録しない。月末の点検（行を入力する問題）の判定は、今までどおりコメントを見ない。

**版のない診療年月のレセプトと試算**（設計書 §11-12）：診療年月に当たる版がないレセプト（改定前の診療年月など）は、取り込みで断らない。コードを区分に引かないまま残し（`UkeReceipt.noRevision`）、一覧には `revisionId: null` と「この診療年月の版はありません（試算できます）」を出す。近い版で代用して点検することはしない。このレセプトは、月末の点検（行を入力する問題）・提出の確定・通知の対応づけ・防いだ額・会議の整理・患者の一覧には並ばない（`src/server/app/uke.ts` の `ukeFiles` に入れない）。ほかのレセプトと見本は、今までどおり動く。

- **試算**（`GET /api/uke/claims/<請求 id>/trial?rev=<版の id>`。事務・ベテラン・事務長。画面は `/uke/<請求 id>` の版の選択）：選んだ版のコードの表・点数表・ルールで、その場で読んで判定した結果を返す。保存しない。日付は UKE のまま動かさない。版のあるレセプトでも呼べる（診療年月の版と違う版を選べば試算）。
- 選べる版は、診療行為コードの表を持つ版だけ（`UKE_TRIAL_REVISIONS`）。令和6年度の版（比較用。コードの表が空）は選択肢に出さず、API に渡しても 400。コードの表が空の版で読むと全部の行が対象外になり、空の結果が「問題なし」に見えるため。
- **点数の違い**：UKE に書いてある 1 回分の点数と、選んだ版の点数が違う単位は、断らずに行を引き、`pointDiffs`（区分・名称・UKE の点数・その版の点数・回数）に並べる。複数の区分がある単位は、区分ごとに分けず、単位の合算どうしを比べる。点検した行の点数と小計は、選んだ版の点数。UKE に書いてある合計は、書いてあるまま別に返す。点数のほかの食い違い（数量データが読めないなど）の単位は、点検の対象外の単位として残す。
- 戻りは試算の型（`trial: { revisionId, claimYearMonth, inPeriod }` と `rulesAvailable` を持ち、判定に使った版 `revisionId`・当たったルール `applied` を持たない）で、提出の確定・適用記録・防いだ額の入口には型で渡せない。患者情報チェックの指摘は返さない。
- 事実・施設の設定は、レセプトの側にあるものだけを使う。選んだ版が読む事実がなければ、情報不足になる（埋め合わせの値を作らない）。版のないレセプトの患者は、試算を開いたときに患者マスタに入る（年齢・保険種別を出すため。ファイルを消すと消える）。
- 試せる合成の UKE：`fixtures/uke/kaiteimae.UKE`（EM 5-1 の表。診療年月は基準月の 7 か月前で、点数は EM §2-9 の令和6年度の値）。令和8年度改定後の版で試算すると、訪問診療料 888／890 と、ベースアップ評価料(Ⅰ) 訪問診療時イ 28／79 が並ぶ。

**保存済みのレセプトの読み直しは、一覧を止めない**（`readStoredUke`）。断るのは取り込みの時だけ。取り込んだ後にコードの表・点数表を直して、保存済みのレセプトの点数が合わなくなった場合は、そのレセプトだけを「取り込んだ後に表が変わり、点数が合わなくなりました」と一覧に出し、点検には並べない。ほかのレセプトは今までどおり動く。形式そのものが読めなくなったファイルは、ファイルごと「読めない」と出す（消すことはできる）。以前の作り物のコードで作られた UKE は、形式が読めれば、行がすべて対象外のレセプトとして出る。

**請求 id はアプリが振る**（`src/uke/upload.ts`）：`U<取り込みの連番>-<ファイルの中の通し番号>`（例 `U12-3`）。連番はクリニックごとに 1 から振り、取り込みの一覧に内容のハッシュと一緒に保存する。消したファイルの連番は使い回さない（一覧に次の連番を持つ）。UKE の「カルテ番号等」は患者の番号として表示にだけ使い、請求 id にも重複の検査にも使わない。別のファイルに、同じ患者・同じ診療年月・同じレセプト種別のレセプトがあるときは、断らずに両方に「同じ月のレセプトがすでにあります」と出す。見本と同じ内容のファイルは見本として取り込み、請求 id は症例の番号（K1〜K7）のまま。

**取り込んだファイルは消せる**（`DELETE /api/uke/uploads/<内容のハッシュ>`。事務長・ベテラン）。消えるもの・残るものは `docs/security.md`。

保存先は、クリニックごとの置き場（`<データの置き場>/tenants/<クリニック>/uke/`）で、名前は内容の SHA-256（`<ハッシュ>.UKE`）。送られたファイル名と請求 id は、パスに使わない。点検では、この置き場のハッシュ名のファイルだけを読み返す（取り込みの一覧は `app_settings` の `uke-uploads`：次の連番と、連番・内容のハッシュの組）。受け取った UKE は取り込みの一覧に並び、同じクリニックの利用者がそれぞれ取り込む。

### 同梱の症例にないレセプトの扱い

UKE に載るのは請求の中身と患者・保険の情報だけで、判定に要るカルテ側の事実は載らない。同梱の症例にないレセプトは、次の形で月末の点検に並ぶ（`src/server/app/cases.ts`）：
- 事実はどれも「不明」。年齢・保険種別だけは、UKE から作った患者マスタで分かる。傷病名の主傷病の印からも主病を埋めない。足りない事実は「情報不足」の指摘として、医療事務か医師への確認に出る。
- 出来事（訪問・往診・処方・退院・死亡・管理料の算定開始月）の記録と過去月の算定はない。施設の設定は `config/facility.json` の標準。
- 出来事の記録を読んで決めるルール（R05・R06・R07・R09・R14）は、記録から出る指摘を出さず、そのルールを情報不足（訪問の記録がそろっているか）として返す。エンジンは載っていない出来事を「なかった」と読むので、そのままでは「要件不足」「区分誤り」と決めつけてしまうため。
- 合計と行ごとの点数は、行だけで決まるので出る。患者情報チェック（P01〜P08）は UKE の患者・保険の情報で動く。
- 対象外：訪問カルテ（書く患者の一覧・訪問の記録に並ばず、保存は断る）、選択モード（始めるときに断る）、練習問題、カルテとの照合（合成カルテがないので不一致は出ない）、査定・返戻の通知の対応づけ（患者は同梱の合成データからだけ引く）。

残るもの：
- コメントは、診療行為のレコードのコメント欄と CO を読み、文字データを捨てない（全角の数字・記号は半角に寄せ、原文も持つ）。コメントコードは形（数字 9 桁）だけを見ている。どの区分に付くかを埋めるのは、帰属が記録の形式から決まるコメント（コメント欄と、単位の途中の診療識別が空の CO）だけで、単位の前後の CO・診療識別つきの CO・レセプト全体へのコメントは、どの区分にも付けない。
- 書き出しの診療識別は、手引きの記録例で確かめた区分（6 区分と包括の検査）のほかは、マスターの点数欄集計先識別の上 2 桁を使っている（記録例では未確認）。読み取りでは診療識別を判定に使わない。
- 受け取った UKE を消す・差し替える手段がない。受け取れる本数にも上限がない（回数制限だけ）。
- 患者は、保険者番号と番号、または氏名・生年月日・性別が同じなら、患者マスタの同じ人にまとめる。受け取った UKE の患者が同梱の症例の患者と重なると、その患者の加入情報に行が足される。
- IR の審査支払機関と保険者番号の食い違い、医療機関コードは確かめていない。
- 「カルテ側の記録がない」を表す専用の事実がないので、情報不足の項目は「訪問の記録がそろっているか」を借りている。画面で入力しても、記録そのものは入らないので、この情報不足は消えない。
